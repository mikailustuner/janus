# Design: FHIR export of the medicine list

> Implements `requirements.md` (2026-11-09). Binding: `.kiro/steering/*.md` (medical-safety,
> privacy, design, tech, structure). No server change; no runtime dependency added.

## 1. Overview
```
list items (store or demo) ──► buildBundle(items, {now, newId, englishName, includeProductNames, demo})
                                   │  pure, src/fhir/bundle.ts
                                   ▼
                     Bundle (collection) ──► serialise ──► Blob(application/fhir+json) ──► <a download>
```
Everything runs in the browser. The builder is pure: the clock, the UUID source and the English
name lookup are passed in, so one input gives one file (P6). The card (`FhirExport.tsx`) supplies
`new Date()`, `crypto.randomUUID` and the vocabulary index.

## 3. The Bundle
```jsonc
{
  "resourceType": "Bundle", "id": "<uuid>", "type": "collection",
  "timestamp": "2026-11-09T10:00:00.000Z",
  "meta": { "tag": [{ "system": "https://github.com/mikailustuner/janus", "code": "generated-by-janus",
                      "display": "Generated by Janus, a research prototype" }],
            "security": [/* demo only */ { "system": "http://terminology.hl7.org/CodeSystem/v3-ActReason", "code": "HTEST" }] },
  "entry": [{ "fullUrl": "urn:uuid:<uuid>", "resource": {
    "resourceType": "MedicationStatement", "id": "<uuid>", "meta": { "tag": [...] },
    "contained": [{ "resourceType": "Patient", "id": "patient" } /*, Medication for a combination */],
    "status": "active",
    "medicationCodeableConcept": { "coding": [{ "system": "http://www.whocc.no/atc", "code": "C09AA05" },
                                              { "system": "http://www.nlm.nih.gov/research/umls/rxnorm", "code": "35296" }],
                                   "text": "ramipril" },
    "subject": { "reference": "#patient", "display": "The person who exported this list (no identifying data)" },
    "effectivePeriod": { "start": "2024-02" },
    "dateAsserted": "2026-11-09T10:00:00.000Z",
    "note": [{ "text": "Generated by Janus, a research prototype, … Not checked by a clinician." }] } }]
}
```
- **Ingredients** (`itemIngredients`): an ingredient candidate gives its key, ATC codes and RxCUIs; a
  product gives one ingredient per published ingredient. A mapped ingredient keeps its ATC codes
  (unless `atc_selection = component_code`) and RxCUIs; an ambiguous one keeps only the person's chosen
  key (name, no codes: the codes on it belong to no single key); an unmapped one keeps its published name.
  Codes are filtered to the shape of their system (ATC `A00AA00` levels 1–5; RxCUI digits).
- **One ingredient** → `medicationCodeableConcept`; **several** → `medicationReference: "#medication"`
  to a contained `Medication` with `code.text` and one `ingredient.itemCodeableConcept` each; **none**
  → a text-only concept.
- **Text:** with "Include product names" the concept's text is the box name (FHIR: "the concept as
  seen by the user"), otherwise the English ingredient name(s).
- **Empty list:** no `entry` (FHIR JSON has no empty arrays); the card is not shown then anyway.

## 4. The card (`FhirExport`)
Placed on the medicines screen after the list, as a `Card` with a `SectionTitle`. Content in order:
title; one-sentence explanation of FHIR; demo line in demo mode; preview count
(`{medicines} medicines, {coded} of {ingredients} ingredients coded`); the checkbox (inside its label,
≥ 44 px) with a hint that box names can identify a person; the primary Download button; the note that
Janus sends the file nowhere and the receiving system decides; a polite `role="status"` line after a
save. The checkbox state is component state only (not stored). Tokens only, no new primitives.
Settings gets no copy of the card (one place keeps one behaviour; DP12).

## 5. Correctness properties
Generators: lists of the 17 recorded demo items in any order and number (0–12), with random box names
(`sentinelBoxName`), start months or none, and random ATC/RxCUI arrays including malformed strings.

| # | Property | Req | Test |
|---|---|---|---|
| P1 | Every item → exactly one Statement; the entry count equals the item count | 1.1 | `bundle.test.ts` |
| P2 | Order kept: entry *i* belongs to item *i* (ids drawn in order) | 1.1 | `bundle.test.ts` |
| P3 | No box name anywhere unless opted in; with the opt-in every item's box name is in its own Statement | 3.1, 3.2 | `bundle.test.ts` |
| P4 | `effectivePeriod.start` equals the item's month and matches the R4 dateTime pattern; absent without a month | 2.5 | `bundle.test.ts` |
| P5 | Every coding has the ATC or the RxNorm system and a code of that system's shape | 2.3 | `bundle.test.ts` |
| P6 | Same items, clock and id source → byte-identical file | 1.1 | `bundle.test.ts` |
| P7 | Every Bundle is valid against the official R4 JSON schema and the R4 rules of Req 1.4; it carries the tag and the disclaimer | 1.4, 4.1 | `bundle.test.ts` |
| P8 | The subject is a contained Patient with no data; no scanned code, NDC, candidate id or dataset version appears | 3.3, 3.4 | `bundle.test.ts` |

Examples: the three demo patients with and without product names are valid; Istanbul gives 9
Statements and 10 of 10 ingredients coded; the Istanbul combination is a contained Medication with two
coded ingredients; a month `2024-13` and an unknown element are rejected by the validator (the
validator really validates). The schema's SHA-256 is checked against the README.

## 6. Decisions
| # | Decision | Alternatives | Why |
|---|---|---|---|
| DP1 | `status = active` for every item | `unknown`; `recorded` (not in R4: it is an R5 `MedicationStatement` status) | The R4 value set (`medication-statement-status`, 4.0.1) defines `active` as "still being taken"; the Janus list is the person's own list of what they take. `unknown` would hide that and receiving systems drop it. The note says the list was entered by the person and not checked by a clinician, which is the honest qualifier. |
| DP2 | One ingredient → `medicationCodeableConcept`; a combination → contained `Medication` with one coded ingredient each | all codings of a combination in one CodeableConcept | Codings in one CodeableConcept mean the *same* concept in different systems; putting amlodipine's and lisinopril's codes together would state that they are one thing. |
| DP3 | Subject = contained `Patient` with only a local id, referenced `#patient`, with a display that says it carries no identifying data | `display`-only reference; a Patient entry in the Bundle | `subject` is 1..1. A contained Patient gives systems that need a resolvable reference a target, while contained resources are not stored on their own, so an import does not create a stray patient record. Display-only references are rejected by many importers. |
| DP4 | Codings only ATC (`http://www.whocc.no/atc`) and RxNorm (`http://www.nlm.nih.gov/research/umls/rxnorm`); no Wikidata QID, Janus J-key, product RxCUI or combination code on a component; no `display` | add QIDs as a Coding; add ATC names | HL7 registers these two URIs; Wikidata and J-keys have none. Product RxCUIs and box codes identify the product the way the box name does. Janus has no reviewed ATC names in English to put in `display`. |
| DP5 | Product names off by default, not remembered | on by default; remembered in settings | Box names can identify a person (rare products, the person's own words); off by default is data minimisation (privacy.md). Not storing the choice keeps the default for every export. |
| DP6 | Generated-by tag on Bundle and Statements; disclaimer in each Statement's `note` | a Janus extension on the Bundle | An extension needs a published StructureDefinition URL Janus does not have; `note` is shown by ordinary viewers and survives when a collection is split into its statements. |
| DP7 | File texts in English (ingredient names, notes, displays) | the interface language | The reader is a receiving system and its staff; English INNs are the reviewed names and match the codings. The card is localised. |
| DP8 | Demo files carry HL7 `HTEST` ("test health data", `v3-ActReason`) in `meta.security` and a demo tag | a file name suffix only | HTEST is HL7's own marker for test data, so a receiving system can see it without reading Janus text. |
| DP9 | File month and timestamps in UTC | local time | `toISOString` is deterministic and an instant needs a zone; differs from local only near midnight at month end. |
| DP10 | Validate with Ajv 8.17.1 (devDependency) and its draft-06 meta-schema; rename the schema's root `id` to `$id` in memory | `@hyperjump/json-schema`; the HL7 Java validator; `ajv@6` (already a transitive dependency) | Ajv is the most used JSON-schema validator for Node, draft-06 support is built in, no Java in CI. The R4 file names its id with the draft-04 keyword while declaring draft-06, which Ajv 8 refuses; renaming that one key changes no rule. A direct devDependency keeps the version pinned instead of relying on eslint's transitive Ajv 6. |
| DP11 | Commit the schema gzipped (287 KB, from 3.4 MB) under `src/fhir/schema/` with a SHA-256 check | fetch in tests; commit uncompressed | CI must run offline; > 1 MB uncompressed. The hash test proves the file is the official one. CC0 allows redistribution; NOTICE names it. |
| DP12 | The card on the medicines screen only | also on Settings | The export is about the list; one place keeps the behaviour and the tests in one spot. |
| DP13 | The JSON schema checks structure, not cardinality or value sets; the test adds the R4 rules it lacks (Req 1.4) | schema only | The R4 schema leaves `status` a free `code` and `medication[x]` optional. Full profile validation (HL7 Java validator, terminology server) is a pre-launch item. |
