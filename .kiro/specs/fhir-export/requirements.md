# Requirements: FHIR export of the medicine list

> Written 2026-11-09 (owner-approved enhancement 5 of 6). Criteria use EARS. **THE client** is the
> web app in `apps/web`. Decisions are in design §6 (DP1…), properties in design §5 (P1…).

## Introduction
A person who keeps their medicine list in Janus may want to hand it to a health system, a pharmacy
app or a clinician's software. FHIR is a standard format many health systems can read. This
feature turns the list into a FHIR R4 (4.0.1) file in the browser and saves it on the device.
Janus sends the file nowhere; what the receiving system does with it is up to that system.

The file restates what the person entered. It is not a clinical record, a reconciliation or advice:
Janus does not check that the medicines are still taken, and the file says so.

## Glossary
- **List item:** one entry of the medicine list `janus.v1.list` (`src/store/list.ts`), or of a demo
  patient's list in demo mode.
- **Bundle:** a FHIR R4 `Bundle` resource of type `collection`.
- **Statement:** a FHIR R4 `MedicationStatement` resource.
- **Coded ingredient:** an ingredient with at least one ATC code or RxNorm RxCUI that Janus holds for it.
- **Product name:** the name on the box (`Item.boxName`). It can identify a person (rare products,
  the person's own words) and is left out by default.

## Requirements

### Requirement 1: The file
**User story:** As a person with a medicine list, I want a standard file of my list, so that another
system can read it without retyping.
#### Acceptance criteria
1. WHEN the person chooses Download THE client SHALL build a FHIR R4 Bundle of type `collection` with
   exactly one Statement per list item, in list order.
2. THE client SHALL build the file entirely in the browser and SHALL save it as a Blob named
   `janus-medicines-YYYY-MM.fhir.json` with the media type `application/fhir+json`.
3. WHILE building or saving the file THE client SHALL NOT send any request (no API call, no upload,
   no analytics).
4. THE Bundle SHALL be valid against the official FHIR R4 JSON schema and SHALL respect the R4 rules
   the schema does not express: `status` from the R4 value set, exactly one `medication[x]`, every
   contained resource referenced, no empty strings or arrays.
5. WHEN the list is empty THE client SHALL NOT offer the download.

### Requirement 2: What each statement says
#### Acceptance criteria
1. Each Statement SHALL have `status` `active` (the list holds the medicines the person says they take; DP1).
2. WHEN an item has one ingredient THE Statement SHALL carry `medicationCodeableConcept` with that
   ingredient's codings; WHEN it has more THE Statement SHALL reference a contained `Medication` with
   one `ingredient.itemCodeableConcept` per ingredient (DP2).
3. Codings SHALL use only `http://www.whocc.no/atc` for ATC codes and
   `http://www.nlm.nih.gov/research/umls/rxnorm` for RxCUIs, and only for codes Janus holds for that
   ingredient. A combination code chosen for a component SHALL NOT code the single ingredient. No other
   code system SHALL appear (DP4).
4. Each ingredient SHALL carry a text name: the accepted English name of its key, else its English
   label, else the name as published.
5. WHEN the start month of an item is known THE Statement SHALL carry `effectivePeriod.start` as
   `YYYY-MM`; otherwise it SHALL carry no effective date.
6. Each Statement SHALL carry `dateAsserted` = the export time.

### Requirement 3: No personal data
#### Acceptance criteria
1. THE Bundle SHALL NOT contain the product name unless the person ticks "Include product names"; the
   box SHALL be unticked by default and SHALL NOT be remembered between visits (DP5).
2. WHEN the person ticks it THE product name SHALL be the text of the medicine's concept (the name the
   person saw), with the ingredient codings unchanged.
3. THE subject SHALL be a contained Patient with no element other than its local id, referenced with a
   display text that says it carries no identifying data (DP3). No name, identifier, birth date,
   address, region or device id SHALL appear.
4. THE Bundle SHALL NOT contain the scanned code, NDC, candidate id, source id or dataset version.

### Requirement 4: Labels
#### Acceptance criteria
1. THE Bundle and each Statement SHALL carry a `meta.tag` saying it was generated by Janus, a research
   prototype, and each Statement SHALL carry the disclaimer in `note` (DP6).
2. WHILE in demo mode THE Bundle SHALL carry the HL7 `HTEST` security label and a "Demo · synthetic
   patient" tag on the Bundle and each Statement (DP8).

### Requirement 5: The card
**User story:** As a person, I want to know what the file is and what happens to it before I save it.
#### Acceptance criteria
1. THE medicines screen SHALL show an "Export as FHIR" card WHEN the list has at least one item, also in demo mode.
2. THE card SHALL say in one sentence what FHIR is, show a preview count (medicines, ingredients coded
   of all ingredients), the "Include product names" checkbox with the reason it is off, the Download
   button, and the note that Janus does not send this file anywhere and the receiving system decides
   what to do with it.
3. WHEN the file is saved THE card SHALL confirm it in a polite live region.
4. WHILE in demo mode THE card SHALL say that the file holds the synthetic demo list.
5. THE card SHALL use the existing primitives (`src/components/ui.tsx`), tokens only, 44 px targets,
   both themes, WCAG 2.2 AA, 375 px and desktop, all five locales (new namespace `Fhir`).
6. THE card's text SHALL NOT advise starting, stopping or changing a medicine and SHALL NOT imply that
   the file is checked, complete or a medical record.

### Requirement 6: Verification
#### Acceptance criteria
1. Property tests SHALL cover design §5 (P1–P8) and SHALL validate generated Bundles against the
   official R4 schema, committed in the repository so that the tests run offline.
2. THE Bundles of all three demo patients SHALL be valid, with and without product names.
3. A Playwright spec SHALL download the file in a demo session, parse it, and check Bundle type, entry
   count, no product names by default, product names when ticked, and that no request was made; and
   SHALL run axe, scroll and target checks at 375 and 1280 px, both themes, five locales
   (`E2E_LOCALES` respected).
